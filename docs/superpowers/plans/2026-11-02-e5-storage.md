# E5 format and partition benchmark implementation plan

> **For agentic workers:** Use superpowers:executing-plans inline; one read-only final review.

**Goal:** Produce measured storage/file/query comparisons and partition-pruning plans for report chapters 6–7.

**Spec:** User E5 screenshot; user selected 100k real rows, 50k each on 2019-11-01/02.

**Architecture:** Extract the first 50k CSV records per date without shifting timestamps or deduplicating. Store one typed C1+event_date multiset as CSV, newline JSON gzip and Delta with/without date partitioning. Preserve Delta versions before/after OPTIMIZE ZORDER so all eight variants can be queried in interleaved order after setup. Capture full row equality, active versus retained physical storage, 72 query timings, scan metrics and EXPLAIN plans.

**Tech stack:** Existing Spark 3.5.3 / Delta 3.2.1 / MinIO, Python, Bash and Matplotlib.

## Constraints and decisions

- No deletion, VACUUM, overwrite of existing targets or existing benchmark edits. Use a unique E5 prefix/container/result directory; retain old Delta files and versions.
- Schema equality: nine C1 columns plus derived date `event_date` for every format; preserve int64 IDs, optional nulls, duplicates and prices.
- Eight variants: CSV/JSON gzip × two layouts; Delta × two layouts × before/after OPTIMIZE ZORDER(user_id,product_id). Existing retention preference remains 30 days.
- Eight write tasks; report actual file counts (partitioning can create more files). OPTIMIZE target128MiB; report combined compaction/ZORDER effect, not independent ZORDER benefit.
- Three data-reading queries: daily event totals/users, product activity/revenue, selective user/product lookup. Round currency in decimal arithmetic; canonical result equality required for every warmup/trial.
- One untimed warmup per variant/query, then three seeded randomized balanced rounds (72 trials). Spark result cache cleared; OS/MinIO/JVM caches stay warm and this is stated explicitly.
- Distinguish selected-file byte sizes from actual IO bytes; pruning requires nonempty partition filters AND runtime selected files below total active files, not merely an EXPLAIN keyword.
- Selected first-N rows are a controlled cohort, not a representative/full-day performance claim.

## Files and tasks

1. `tests/test_e5_storage.py`, `src/monitoring/e5_storage.py`: failing boundary tests for extraction quotas, types/multiplicity, query inputs, trial matrix, complete aggregations and pruning evidence. Implement pure helpers after RED.
2. `src/monitoring/e5_storage.py`: Spark preparation, isolated table writes, pinned snapshots, exact multiset checks, OPTIMIZE, active/physical listings, timed queries and metrics. Save immutable per-trial JSON immediately.
3. `src/monitoring/e5_report.py`: rebuildable CSV/Markdown tables and standalone plots from complete validated trials; retain truthful limitations.
4. `benchmarks/e5_storage.sh`, `Makefile`, README/runbook: separate Spark controller sharing master's network; scoped readonly source/code mounts, writable E5 result directory. No .git or whole-workspace mount.
5. Run unit suite, Bash/Compose checks and independent read-only review; execute actual E5 on two healthy workers without competing Spark applications. Verify result equality, eight snapshots, all72 trials, pruning and report/chart artifacts.

## Review focus

- Missing day/quota, malformed or overflowing values must fail without silently shortening input.
- Missing/repeated trial cells, mismatched result hashes or nonfinite timings cannot produce a PASS summary.
- Keep old Delta files so pre-OPTIMIZE snapshots are real and physical footprint includes retention.
- No cached DataFrame substitution or metadata-only COUNT query in measured plans.
- Report evidence on every format/layout, not only the fastest variant; preserve slow timings and setup failures.
